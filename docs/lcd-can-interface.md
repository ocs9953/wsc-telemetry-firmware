# LCD 대시보드 ↔ 텔레메트리 보드 CAN 인터페이스

**대상**: 차량 대시보드(LCD) 팀
**상태**: ID·필드는 **잠정값**(배관 검증용). 협의 후 확정한다.
**최종 수정**: 2026-08-30

---

## 0. 가장 먼저 읽을 것 — 명령은 반드시 반복 전송해야 합니다

텔레메트리 보드의 CAN 컨트롤러(MCP2518FD)는 **평소 슬립 상태**이고,
버스에 신호가 오면 스스로 깨어납니다. 문제는 **깨우는 프레임 자체는 유실된다**는
점입니다. 오실레이터가 안정화되는 데 최대 3 ms 가 걸리고(데이터시트 Table 7-3
TOSCSLEEP), 500 kbps 에서 3 ms 는 프레임 1~2개 분량입니다.

> **명령을 1회만 보내면 조용히 사라집니다.**
> 반드시 **20 ms 간격으로 5회 연속(총 100 ms)** 반복 전송해 주세요.

반복 횟수와 간격에는 상한이 있습니다.

| 제약 | 값 | 이유 |
|---|---|---|
| 한 버스트의 프레임 수 | **최대 8** | 보드 수신 FIFO 가 8칸. 넘치면 뒤쪽이 버려집니다 |
| 버스트 총 길이 | **200 ms 이내** | 보드는 마지막 수신 후 200 ms 가 지나면 다시 잠듭니다 |
| 버스트 간 간격 | **최소 200 ms** | 아래 100 ms 간격 제한과 겹치지 않게 |

권장값(20 ms x 5회)은 이 세 조건을 모두 만족합니다.

보드 쪽은 중복을 알아서 걸러냅니다(§2의 100 ms 간격 제한). 반복분 중 실제로
VCU 에 전달되는 것은 **1회뿐**이므로, 반복 때문에 명령이 두 번 적용되는 일은
없습니다.

이 때문에 **명령은 "상태(state)"로 설계해 주세요.** "크루즈 목표속도 = 60"은
안전하지만, "크루즈 ON/OFF 토글"은 반복 전송과 궁합이 나쁩니다.

### 왜 상시 깨움으로 안 하나요

3.3 V 레일 전류 예산이 빠듯합니다. LDO(TLV70433)의 전류 제한이 최소 160 mA 인데,
MCP 를 항상 깨워 두면 +15 mA 가 상시로 붙어 피크가 138 mA → 153 mA(96%)가 됩니다.
PCB 는 이미 발주된 상태라 회로 변경이 불가능합니다.

### 보드가 0x501 을 보낼 때 깨어 있지 않나요

보드는 0x501 을 100 ms 마다 보내므로 실제로는 거의 항상 깨어 있습니다. 다만 그것에 기대지 마세요 — 발행 주기나 전력 정책이 바뀌면 다시 잠들게 됩니다. **보드의 송신 타이밍에 맞춰 보내는 방식으로는
문제를 피할 수 없습니다.** 반복 전송이 유일한 해법입니다.

## 2. LCD → 보드 (명령)

| 항목 | 값 |
|---|---|
| 사용 가능 ID | **0x510 ~ 0x51F** (보드 수신 필터가 이 대역만 통과) |
| 현재 구현된 ID | **0x510** |
| DLC | **2 이상** (미만이면 폐기) |
| 최소 전송 간격 | **100 ms** — 그보다 빨리 온 프레임은 조용히 폐기 |

### 페이로드 (0x510) — ACC 명령 (2026-09-03 LCD 팀 확정)

| 오프셋 | 크기 | 내용 | 범위 |
|---|---|---|---|
| 0 | 1 B | ACC 설정속도 (u8, km/h) | **0~150** |
| 1 | 1 B | ACC 상태 (u8) | **0=OFF, 1=ON** |
| 2~7 | 6 B | 미사용 (0 채움) | — |

설정속도는 상태가 OFF 여도 계속 실립니다(대기 중인 설정값). 수신측은
byte 1 이 0 이면 byte 0 을 무시하면 됩니다.

보드는 앞 **2바이트만** 꺼내 VCU 버스(Bus A)로 **ID 0x420**, DLC 2 로 중계합니다.
나머지 바이트는 버립니다. 필드를 byte 2 이후로 늘리려면 보드 팀과 중계 폭을
먼저 합의해야 합니다 — 지금은 도달하지 않습니다.

**범위 검증**: 보드는 `설정속도 > 150` 이거나 `상태 > 1` 인 프레임을 **통째로
버립니다**(클램프하지 않음). 쓰레기 값을 접어서 넘기면 VCU 가 그것을 운전자의
정상 명령으로 취급하기 때문입니다. 전달이 끊기면 VCU 쪽 타임아웃으로 ACC 가
해제되는 방향이라 안전한 쪽으로 실패합니다.

### 100 ms 간격 제한이 반복 전송과 맞물리는 방식

보드는 **직전에 VCU 로 중계한 시점부터 100 ms 안에 들어온 프레임을 버립니다.**
LCD 가 고장 나 같은 프레임을 쏟아낼 때 차량 버스를 막지 않기 위한 장치입니다.

권장 버스트(20 ms x 5회)에서는 이렇게 동작합니다.

| 시각 | 프레임 | 결과 |
|---|---|---|
| 0 ms | 1회차 | **유실** (보드를 깨우는 데 소모) |
| 20 ms | 2회차 | **VCU 로 중계됨** |
| 40/60/80 ms | 3~5회차 | 간격 제한으로 폐기 |

즉 **버스트 1개 = VCU 명령 1회**입니다. 반복해도 중복 적용되지 않습니다.

다만 **연속된 두 버스트의 시작 간격이 200 ms 미만이면** 두 번째 버스트의 앞
프레임이 간격 제한에 걸려 반응이 한 박자 늦습니다. 명령을 연달아 바꿔야 하는
UI(예: 다이얼을 빠르게 돌리는 경우)라면 **최종 값만 200 ms 마다 보내는 방식**으로
만들어 주세요.

> 전달할 명령 항목(크루즈 목표속도 등)이 정해지면 알려주세요. 보드 쪽에서
> 범위 검증을 추가한 뒤 확정합니다. 지금은 검증 없이 그대로 통과시키고 있어
> **실차 적용 전에 반드시 확정해야 합니다.**

## 3. 보드 → LCD (대시보드 표시값)

| 항목 | 값 |
|---|---|
| ID | **0x501** |
| 주기 | **100 ms** (10 Hz) |
| DLC | **8** |
| 바이트 순서 | **리틀엔디안** 전부 |

| 오프셋 | 타입 | 필드 | 단위 | 비고 |
|---|---|---|---|---|
| 0 | u16 | 차속 | 0.01 m/s | 예: `1234` → 12.34 m/s |
| 2 | **i16** | 버스 전류 | 0.1 A | **회생 시 음수** |
| 4 | u16 | SOC | 0.1 % | 0 ~ 1000 (= 0 ~ 100.0 %) |
| 6 | **i16** | 모터 전력 | 1 W | **회생 시 음수**, ±32.7 kW |

모터 전력은 보드가 `버스전압 × 버스전류`로 계산해서 넣습니다(별도 CAN 신호 아님).

### 부호 있는 필드 — 테스트 벡터

byte2-3(전류)와 byte6-7(전력)은 **i16 2의 보수**입니다. 회생 중에는 음수가 실립니다.
unsigned 로 읽으면 값이 조용히 6만대로 튀므로, 아래 두 프레임으로 파서를 검증하세요.

실측 프레임입니다(2026-09-02, 모터 더미 연결 상태에서 보드가 실제로 내보낸 값):

```
구동 최대   58 09 D7 02 96 03 60 22
회생 최대   3A 07 41 FF 18 03 36 F7
```

`회생 최대` 프레임의 올바른 해석:

| 오프셋 | 원시(LE) | u16 으로 읽으면 | **i16 (정답)** |
|---|---|---|---|
| 0-1 차속 | `0x073A` | 1850 | 1850 → **18.50 m/s** |
| 2-3 전류 | `0xFF41` | 65345 → 6534.5 A | −191 → **−19.1 A** |
| 4-5 SOC | `0x0318` | 792 | 792 → **79.2 %** |
| 6-7 전력 | `0xF736` | 63286 → 63286 W | −2250 → **−2250 W** |

**판정법**: 모터 더미를 물린 상태에서 전력이 계속 0 이상으로만 보이거나, 가끔
6만대 값이 스쳐 지나가면 부호 처리가 빠진 것입니다.

현재 더미 기준 정상 표시 범위는 다음과 같습니다(60초 주기 삼각파):

| 필드 | 범위 | 음수 구간 비율 |
|---|---|---|
| 차속 | 0 ~ 25 m/s | — |
| 전류 | −19 ~ +78 A | 약 40 % |
| 전력 | **−2250 ~ +8800 W** | 약 42 % |

즉 **전력은 시간의 약 40 %를 음수로 보내고 있습니다.** 화면에 음수가 한 번도
안 나온다면 그건 값이 안 오는 게 아니라 파싱 문제입니다.


### 값이 안 올 때

보드는 해당 CAN 신호를 못 받아도 0x501 을 계속 보냅니다. 이때 필드에는
**마지막으로 받은 값이 그대로 남습니다**(0 으로 초기화되지 않음). LCD 쪽에서
"값이 오래됐다"를 판단할 수단이 현재 프레임에 없습니다 — 필요하면 알려주세요.
freshness 플래그를 넣을 자리를 만들어야 합니다.

## 4. ID 대역 요약 (충돌 방지)

| 대역 | 용도 | 방향 |
|---|---|---|
| 0x500 ~ 0x50F | 보드 → LCD | LCD 는 **송신 금지** |
| 0x510 ~ 0x51F | LCD → 보드 | LCD 송신 |

0x510~0x51F 이외의 ID 는 보드 수신 필터에서 하드웨어적으로 걸러지므로
**보드에 도달하지 않습니다.**

## 5. 확정 필요 항목

- [ ] LCD → 보드 명령의 실제 내용과 값 범위 (→ 보드에 검증 코드 추가)
- [ ] 대시보드 표시 항목이 위 4개로 충분한지 (부족하면 0x502 추가)

## 6. 통합 테스트 시 확인할 것

1. LCD 전원만 켠 상태에서 CAN-H ↔ CAN-L 저항 측정 (종단 2개면 약 60 Ω)
2. LCD → 0x510 반복 전송 → 보드 Bus A 에 0x420 이 뜨는지 (100 ms 에 1회)
3. **반복 없이 1회만** 보내 유실되는지 확인 — 유실돼야 정상입니다(§0)
4. 버스트를 200 ms 미만 간격으로 연달아 보내 두 번째가 늦게 반영되는지 확인(§2)
5. 보드 → **0x501** 이 100 ms 주기로 나오는지, 필드 스케일이 맞는지
