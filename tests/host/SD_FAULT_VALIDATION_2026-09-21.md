# SD 장애 검증 — 2026-09-21

2026-09-18 기록의 후속이다. 그때 남은 두 경계 조건(굳음을 처음 본 호출이
HAL 로 내려가는 문제, 재마운트 뒤에도 남는 1ms 대기 한도)을 고친 코드로
다시 측정했고, 판정 기준을 "복구 성공" 하나에서 아래 지표들로 넓혔다.

## 환경 및 방법

- 벤치 구성. **CAN 은 연결되어 있지 않다** — 버스 관련 판정은 이 기록의 범위가 아니다.
- ELF: `build/bench/WSC_Transmitter_Code_V1.elf`
- ELF SHA-256: `932b01c982e024e4936e43c6325b347d81fa87708f4ad67294a93380b1cd5a04` (idle 시험 시점)
- 게이트: PHASE25/4/45/5/6/8/9 = 1, PHASE7 = 0, TEST_DUMMY_DATA = 0
- 주입: SDMMC1 IRQ78 만 NVIC 에서 차단해 DMA 완료 통지를 누락시킨다. 실제
  완료 대기·타임아웃·복구 경로가 그대로 실행되며 카운터를 직접 조작하지 않는다.
- 관측: OpenOCD telnet 4444 로 메모리만 읽는다. halt·reset 없음.
- 도구: `tests/host/sd_irq_fault.js` (`--hold-ms`, `--repeat-mask` 추가)

### 지속 장애를 만드는 방법 (이번에 알게 된 것)

한 번만 IRQ 를 막으면 장애가 1~2초 만에 저절로 끝난다. 복구 경로의
`MX_SDMMC1_SD_Init` → `HAL_SD_MspInit` 이 NVIC 를 **스스로 다시 켜기**
때문이다. 20초를 걸어도 결과가 같았다. 그래서 `--repeat-mask` 로 샘플마다
마스크를 다시 걸어 "계속 응답하지 않는 장치"를 만들었다.

두 점은 "일정 생성률 × (유지 시간 + 고정 지연)" 으로 설명된다 —

장애 지속시간으로 설명되며, 복구 후 12초 관찰에서 카운터는 908 에 멈춰 있었다.

### 계측 공백을 하나 메웠다

레코드는 큐가 아니라 **로거 안에서** 버려진다 — 매체가 없으면 큐에서 꺼낸 뒤
버린다(`sd_logger.c`, Req 8.5). 의도한 동작이지만 세는 곳이 없어서, 큐 적체로도
`g_sd_q_drops` 로도 잡히지 않았다. `g_sd_discarded` 를 추가했다. 위 표의
"버려진 레코드"가 그 값이다.

## idle 진입 무응답 (`tests/host/sd_idle_stall.js`)

앞의 주입은 전부 상태 머신이 **도는 중**에 발견되는 경우다. 남은 질문은
반대쪽이었다 — 가드가 볼 때는 idle 이라 HAL 질의로 내려보냈는데 그 뒤에 카드가
대답을 멈추는 경우.

만드는 방법: SDMMC 가 idle 일 때 RCC 에서 클럭을 끊는다(AHB2ENR1 비트 27).
클럭이 없으면 카드가 CMD13 에 대답할 수 없고, 하드웨어 명령 타임아웃(SDMMC_CK
64클럭)도 진행하지 않는다. `POWER.PWRCTRL` 을 0 으로 쓰는 방법은 이 부품에서
**쓰기가 무시된다** (벤치 확인).

| 코드 | 결과 |
| --- | --- |
| 고침 전 | 6.6초 뒤 리셋, `g_boot_reset_csr` = **IWDG** |
| CMD13 상한만 추가 | 4.6초 뒤 리셋, 여전히 **IWDG** |
| 재시도 창까지 좁힌 뒤 | 12초·15초×3회 모두 **리셋 없음**, 복구 성공 |

### 왜 한 호출을 짧게 만드는 것으로 부족했나

디버거로 정지시켜 PC 를 읽으니 새로 넣은 대기 루프 안이었다. 한 호출은 50ms
안에 끝나지만 `check_sd_status` 가 그것을 750ms 동안 반복하고, 파일 쓰기 하나는
섹터마다 요청을 낸다. 막는 것은 **한 호출이 아니라 누적**이었다. 그래서
`FX_STM32_SD_DEFAULT_TIMEOUT` 을 함수로 바꿔, 복구가 필요하다고 판단된 뒤에는
재시도 창을 1틱으로 좁힌다.

### 기존 경로 회귀 확인

인터럽트 차단 주입 3회 재실행 — 모두 타임아웃 검출·복구 성공, 리셋 없음.

  응답만 늦추는 실제 불량은 별개이며, 그쪽은 카드 자체가 있어야 한다.
- **CAN 연속성**: 별도 기록으로 닫았다 — `CAN_CONTINUITY_2026-09-21.md`.

## 코인 배터리(VBAT) 미장착 영향 검토 — 2026-09-28

이날 시험은 **BAT 코인 배터리 없이** 진행됐다(사용자 확인). 코드 변경과 판정에
영향이 있었는지 되짚었다.

### 회로

넷리스트(WSC.kicad_sch 에서 추출): VBAT 네트는 **H1(코인 홀더) · C24 · MCU VBAT(6번)**
뿐이고 3.3V 와 이어져 있지 않다. 코인이 없으면 VBAT 핀이 뜬다 — 데이터시트는
배터리를 안 쓸 때 VBAT 를 VDD 에 묶으라고 한다. NRST 는 **J1(SWD 커넥터) · SW4(버튼)**
· C15 · D1 에 연결돼 있다.

### 펌웨어가 백업 도메인에 두는 것

RTC 캘린더와 LSE, BKP1R(RTC 초기화 표식 = 빌드 스탬프), BKP2R(스택 오버플로 표식).
VDD 가 유지되는 동안은 VBAT 가 없어도 백업 도메인은 VDD 로 동작한다. 차이는
**전원을 껐다 켤 때만** 난다.

### 판정에 영향 — 없음

- 판정 근거가 전부 백업 도메인 밖이다: 시간 = `uwTick`(HAL_GetTick), 리셋 원인 =
  RCC_CSR(`g_boot_reset_csr`), 복구·유실·CAN 계수 = SRAM 변수.
- 이날 증거 전체의 리셋 원인 분포: PIN 500 · SOFT+PIN 88 · IWDG+PIN 12 · **BOR+PIN 5**.
  BOR+PIN 은 20:04 경 한 번의 전원 재투입(CAN 배선 시점)이다. 전원 재투입이
  제대로 BOR 로 찍혔다는 것 자체가 RCC_CSR 이 정상이었다는 근거다.
- 레코드 타임스탬프는 uwTick 이라, 앞서 확인한 "시각 역전 없음" 도 영향이 없다.

### 코드 변경에 영향 — 없음

9/18~9/23 커밋 중 RTC · LSE · 백업 도메인을 건드린 것은 없다(rtc.c 마지막 변경 9/02,
main.c 9/18 — 부팅 원인 캡처 추가). 시각이 이상하다는 증상에 대응해 바뀐 코드는 없다.

### 영향이 있던 곳 — 표면적

- 20:04 전원 재투입 뒤 RTC 가 **빌드 시각에서 다시 출발**했다. 그 뒤의 SD 파일명과
  10초 RTC 기록은 실제 시각보다 (전원 투입 − 빌드 시각) 만큼 뒤처졌다. 판정에는
  쓰지 않은 값이다.
- 참고: 새 빌드를 구울 때마다 RTC 는 코인 배터리와 무관하게 빌드 시각으로 다시
  맞춰진다(BKP1R 표식이 빌드 스탬프라서). 이날은 계속 새로 구웠으므로 차이는 작다.

### 조작 없는 PIN 리셋(20:53)과의 관계 — 설명하지 못한다

그 리셋은 PIN 단독이다(BOR 없음) — VDD 가 흔들린 게 아니다. VBAT 가 떠 있어도 NRST 를
당길 경로가 없다. 코인 배터리는 원인 후보에서 빠지며, 원인 분리 계획(디버거를 뺀
관측)은 그대로 유효하다.

### 참고 — 콜드 부팅

VBAT 가 없으면 전원을 켤 때마다 LSE 가 냉기동한다(`LSE_STARTUP_TIMEOUT` 5초).
IWDG 는 그 뒤(`MX_IWDG_Init`)에 켜지므로 워치독과는 무관하고, 부팅 시간만 늘어난다.

### 권고

실차와 벤치 모두 **코인 배터리를 장착**한다. PCB 수정이 불가해 VBAT-VDD 연결은
할 수 없다.
