# CAN 연속성·계측 검증 — 2026-09-21

`SD_FAULT_VALIDATION_2026-09-21.md` 의 "CAN 미연결이라 범위 밖" 항목을 닫는 기록이다.
2026-09-18 판정이 틀렸던 이유도 여기서 정리한다 — 그때는 누적 수신 수만 보고
"연속성 통과" 로 적었는데, 누적 수는 끊긴 구간을 숨긴다.

## 구성

- Bus A(FDCAN1): MPPT 더미 1대 (4유닛 모사, 약 58프레임/초)
- Bus B(MCP2518FD): 0x510 을 약 4.9프레임/초로 보내는 노드
- 관측: OpenOCD telnet 4444 메모리 읽기. `tests/host/can_watch.js`
- 구간 초기화: `tests/host/can_reset_stats.js`

## 순번 하트비트

실제 프레임은 8바이트가 전부 물리량이라 순번을 넣을 자리가 없다. 더미가 전용
ID 로 32비트 카운터만 따로 보낸다. MPPT 더미의 `DUMMY_HEARTBEAT_ID` 를
`ID_TEST_HEARTBEAT_BUS_A`(0x4FE) 로 켰다. **버스당 한 대만** 켜야 한다.

## 무장애 기준선 (30초)

| 지표 | 값 |
| --- | --- |
| Bus A 최대 프레임 간격 | 100ms — 하트비트 주기가 곧 상한이 된다 |
| Bus A 순번 수신 / 누락 / 재시작 | 304 / 0 / 0 |
| Bus A 유실 · 길이부족 · bus-off | 0 / 0 / 0 |
| Bus B 최대 간격 · 넘침 · TEC/REC | 204ms / 0 / 0,0 |

## SD 장애 중 연속성

두 장애 모두 SD 는 실제로 끊겼다(타임아웃 발생, 레코드 버려짐, 복구 성공).

| 장애 | SD 결과 | Bus A 순번 수신/누락 | Bus A 최대 간격 | Bus B |
| --- | --- | --- | --- | --- |
| 인터럽트 차단 10초 지속 | 타임아웃 5, 복구 1, 297 버림 | 342 / **0** | 101ms (기준선과 동일) | 간격 204ms, 넘침 0 |
| idle 정지 15초 | 복구 1, 22 버림, 리셋 없음 | 160 / **0** | 100ms | 간격 204ms, 넘침 0 |

프레임 단위로 한 개도 빠지지 않았고, 최대 간격이 기준선에서 움직이지 않았다.
"총 개수가 늘었다" 가 아니라 "끊긴 구간이 없었다" 를 말할 수 있는 근거다.

## 포화 시험 (S4, 더미 버스트 모드)

약 1,600프레임/초로 약 50초. **유실 0, 순번 누락 0, 최대 간격 1ms.** 수신 ISR 이
버스 최대 속도를 따라간다. 부수 결론: 정상 동작만으로는 유실 카운터를 확인할 수
없다.

## 유실 카운터가 실제로 세는지 (`can_rx_lost_inject.js`)

포화 상태에서 FDCAN1_IT0(IRQ39)을 300ms 막아 FIFO 를 강제로 넘겼다.

| 지표 | 변화 | 맞는가 |
| --- | --- | --- |
| `g_can_rx_lost` | 0 → 2 | 유실 사건 발생 |
| `g_can_seq_missed` | 0 → 3 | 10프레임/초 × 0.3초 = 3 |
| `g_can_gap_max_ms` | 1 → 304 | 차단 시간 300ms |

서로 독립적인 세 지표가 주입 시간과 맞는다.

## 아직 아닌 것

- **Bus B 넘침(`g_mcp_rx_ovf`)** 은 미검증이다. Bus B 에 있는 노드를 우리가 프로그램할
  수 없어 포화를 만들지 못했다. 코드 경로는 FIFO 상태값을 이미 읽는 자리에 있다.
- **Bus B 순번** 도 같은 이유로 못 켰다. Bus B 연속성은 프레임 간격·TEC/REC 로만
  판정했다.
- 시험이 끝난 뒤 더미의 `MPPT_BURST_MODE` 는 0 으로 되돌려 다시 구웠다(확인함).
