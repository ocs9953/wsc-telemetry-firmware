## E. 장애 주입 재확인

관측 도구(`observe_bench.js`, 90초)를 먼저 띄우고 주입했다.

| 항목 | SD IRQ 차단 | idle 진입 반복 차단 |
| --- | --- | --- |
| 리셋 | 없음 | 없음 |
| 최종 SD 상태 | 정상 복귀 | 정상 복귀 |
| 관측 구간 | 90.090초 | 89.917초 |
| Bus A 하트비트 누락 / 수신 | 0 / 901 | 0 / 899 |
| Bus A FIFO 유실 / Bus B 넘침 | 0 / 0 | 0 / 0 |
| 큐 드롭 무선/SD | 0 / 0 | 0 / 0 |
| 종료 후 RTOS | 7/7, 8/8 | 7/7, 8/8 |

- 수치는 관측 도구의 최종 원본에서 다시 뽑았다. 처음 적은 idle "0 / 664" 는 관측이
  아직 돌던 약 66초 시점의 중간 집계였다 (리뷰 지적).
- **두 관측 구간이 겹친다.** SD IRQ 쪽 관측(20:03:09–20:04:39)이 끝나기 전에 idle
  주입(20:04:22–20:04:36)이 시작됐다. 그래서 IRQ 관측의 SD 수치(복구 2회, 폐기 669,
  쓰기 손실 64)에는 idle 주입분(복구 1, 폐기 345, 쓰기 손실 32)이 섞여 있다. 주입
  스크립트 자체가 잰 IRQ 단독 값은 복구 1회, 폐기 324, 쓰기 손실 32. 하트비트·유실·
  드롭 0 이라는 결론은 겹침과 무관하게 같다. 다음부터는 관측이 끝난 뒤 다음 주입을 건다.
- SD IRQ: 10초 차단(`--hold-ms=10000 --repeat-mask`). 차단 시작부터 정상 복귀까지
  약 12초. 이 스크립트는 `measuredOutageMs` 를 기록하지 않는다 — 12초는 샘플의
  상태 전이에서 읽은 값이다.
- idle: 약 12초 동안 반복 차단을 걸었다. 첫 클럭 복구는 약 360 ms 뒤였고
  (`measuredOutageMs`), 이후 3회 재차단했다(`clockRegates`). 리셋 없이 최종 복구됐다.
  **각 차단 구간의 길이는 측정하지 않았다** — "0.36초씩 세 번" 이 아니다.

## F. Bus B 연속성 — 결함 발견

BMS 라벨 보드에 모터 펌웨어(하트비트 0x51F)를 구워 Bus B 에 연결했다.
(`WSC_DUMMY_SN=066DFF555185754867225014 bash build_dummy.sh Motor flash`)

처음 측정: 10초에 하트비트 100개, "누락" 9,900. 더미 RAM 의 순번(`hb_seq`)은 2초에
20 증가 — 송신은 정상. 한 프레임마다 100(= 송신 시각 ms 의 100 ms 주기 증가분)씩
뛰었다.

원인: `MCP251XFD_ReceiveMessageFromFIFO()` 는 FIFO 설정이 아니라 **타임스탬프
포인터가 NULL 인지**로 RAM 객체의 타임스탬프 4바이트 유무를 판단한다. FIFO1 에는
타임스탬프를 켜지 않았는데 포인터를 넘겨, 모든 Bus B 프레임의 data[0..3] 에 원래
byte 4..7 이 들어왔다. 영향: LCD 0x510(설정속도·ON/OFF) → VCU 0x420 중계가 엉뚱한
바이트를 읽고 있었다 (PHASE7 은 벤치에서 꺼져 있다).

수정 후 30초: 하트비트 300, 누락 0, 재시작 0, 넘침 0, 최대 간격 103 ms.

아직 안 본 것: 실제 디스플레이로 0x510 → 0x420 중계 값.

**BMS 라벨 보드에는 지금 모터 펌웨어가 들어 있다.** 되돌리려면
`bash build_dummy.sh BMS flash`.

## G. FAT 읽기 전용 검사

- 먼저 백업: 파일 264개, 27,780,248 바이트 → `build/sd_backup_20260928/`,
  SHA-256 전부 일치 (복사가 정확했다는 뜻이지, 원본이 온전하다는 증명은 아니다).
- 리뷰어가 백업 로그 262개, 1,736,260 레코드의 CRC 를 검사해 오류 0.
- `chkdsk E:` (옵션 없음): **잃어버린 체인 1개, 32 KB (클러스터 1개)**. 그 외 오류 없음.
  고치지 않았다. 나중에 포맷이나 `chkdsk /F` 로 정리하면 된다.
- 처음 줄의 "Access is denied" 는 관리자 권한이 없어 볼륨을 잠그지 못했다는 뜻이다.
  검사는 끝까지 돌았다.

라디오는 오늘 COM11 → (선 교체 후) COM9 로 잡혔다. 판정은 보완한
`radio_reset_watch.js --expect-seconds=1800` (`a34cfc5`) 로 했다.

| 조건 | 결과 |
| --- | --- |
| 1-A 디버거 없음 (SWD 커넥터를 보드에서 분리) | **리셋 없음.** 0.0–1800.0초 끊김 없이 수신, 패킷 41,100, 오류 0, 최대 공백 0.64초 |
| 1-B 디버거 연결 + OpenOCD 접속 | **리셋 없음.** 0.0–1799.9초 끊김 없이 수신, 패킷 41,277, 프레이밍 오류 1 (CRC 0), 최대 공백 0.64초 |

판정표: **둘 다 없음 → 재현 안 됨.** 가만히 둔 상태로는 30분씩 두 조건 모두 PIN 리셋이
나지 않았다. 9/21 리셋은 오늘 조건으로는 재현되지 않았고, 원인 후보로 남은 것은
아래 관찰(SWD 케이블 쪽을 건드리거나 ST-LINK 전원이 빠지는 경우)이다.
다음은 판정표대로 조건을 넓힌다 — 케이블만 꽂힌 상태의 NRST 전압 측정, 그리고
9/21 처럼 도구가 SWD 로 주기적으로 읽는 상태에서의 관찰.

(1-B 판정은 자동 실행 확인이 일시적으로 막혀 사용자가 직접 돌린 출력으로 기록했다.)

관찰 (가설, 측정 아님):
- 사용자 관찰: **케이블을 보드에 꽂은 채 ST-LINK 를 PC 에서만 빼면 보드가 계속 리셋된다.**
  전원 없는 ST-LINK 가 NRST 를 끌어내린다는 설명과 맞지만 NRST 전압은 재지 않았다.
- 1-B 시작 때 가동 시간 2,502초, 마지막 원인 PIN → 마지막 리셋은 약 20:24,
  1-A 를 위해 커넥터를 뺀 시점과 맞는다. 1-A 캡처는 그 뒤에 시작했다.
- 1-B 로 가며 커넥터를 꽂을 때(ST-LINK 를 PC 에 먼저) 는 리셋이 없었다.
